# realMemory v0.4: единое хранилище, скоупы global/проекты, гибридный поиск

Топология (мой выбор, обсуждение осталось без ответа): **одна база + скоупы на следах**. Каждый след помечен `scope='global'` (предпочтения, факты о пользователе) или именем проекта. `recall` ищет в {текущий проект, global}. Namespace-изоляция остаётся как есть для жёсткой изоляции. Порядок: WP1→…→WP6, коммит после каждого, тесты зелёные между этапами.

## WP1. Единое хранилище — фикс бага «last-writer-wins» (+ мелочь про pickle и ротацию)

Всё мутабельное состояние вне SQLite (рёбра L2, eligibility, счётчики, журнал) переезжает в `memory.db`:

1. Новые таблицы: `edges(src,dst,w, PK(src,dst))`, `eligibility(seq,src,dst,strength,created_at)` + `elig_sources(seq,mem_id)` для reward-матчинга, `events(seq,ts,type,data-JSON)`; в `db_meta`: `last_edge_tick`, `last_consolidate_at`, `pending_reward_touches`, `schema_version`.
2. Записи через `BEGIN IMMEDIATE` (`isolation_level=None`; busy_timeout=5000 уже стоит) — два процесса больше не затирают друг друга.
3. `EligibilityLog` — write-through: `add()`=INSERT, `reward()`=UPDATE по elig_sources, `commit()`=SELECT+DELETE в одной транзакции.
4. `AssemblyNetwork` — ленивый распад вместо O(E)-на-запись (закрывает долг из бэклога): эффективный вес `w·exp(−Δt/τ)` от `db_meta.last_edge_tick` при чтении; CSR-кэш строится на открытии, инвалидация по `PRAGMA data_version`; prune и тик — только внутри consolidate-транзакции (Δt от last_tick после захвата блокировки ⇒ двойного распада нет).
5. `Journal` → таблица `events` (API `append/events/count` сохраняется); существующий `journal.jsonl` импортируется однократно, файл → `.imported`. Ротация не нужна.
6. `snapshot.pkl` упраздняется: при открытии legacy-снапшот импортируется в таблицы один раз (флаг в db_meta), файл → `.imported`. `save()/_load_state` удаляются; `stats()` агрегирует events + COUNT.
7. Троттлинг sleep-хука: `last_consolidate_at` + `max(updated_at)` вместо mtime снапшота.
8. Тесты: новый `test_multi_process_state.py` (два Hippocampus на одной директории, interleaved: eligibility процесса A доезжает до консолидации B, счётчики не теряются). Обновить `test_store_journal`, `test_report`, `test_hook_cli`, интеграцию save/reload.

## WP2. Скоупы global/проект

1. `MemoryRecord.scope` (default `'global'`), колонка + индекс, миграция: записи id 2,6 → `'realMemory'`, прочие → `'global'`.
2. `remember(..., scope)`: `_probe` фильтрует кандидатов `scope IN ({scope},'global')` — гейт не сливает проекты. Связи L2 не ограничиваются, фильтрация на чтении.
3. `recall(..., scope, all_scopes=False)`: обе волны фильтруются `scope IN ({scope},'global')`; `scope=None` → без фильтра (как сейчас).
4. `resolve_project()`: параметр тула `project` > env `REALMEMORY_PROJECT` > basename(cwd), если в cwd есть `.git`/`.zcode` > None.
5. MCP: `recall/memorize` получают `project: str|None`; `introspect` показывает разрешённый проект. Хукам — `${ZCODE_PROJECT_DIR}` (обновлю `~/.zcode/cli/config.json`).
6. Тесты: изоляция проектов, глобальные видны везде, probe не смешивает, бриф уважает скоуп.

## WP3. Гибрид FTS5 + пороги под эмбеддер

1. `memories_fts` (fts5, content=memories) + триггеры; понятная ошибка, если сборка SQLite без FTS5.
2. Recall: токены запроса (в кавычках, OR) → bm25-кандидаты объединяются с L1 до реранка; канал `source='keyword'` для совпадений ниже cos_min_recall с пониженной уверенностью; FTS участвует и в `_probe` (дубликаты с точными токенами).
3. Профиль порогов для fastembed по моим замерам (случайные пары ≤0.258, переформулировки ≥0.59): `theta_link≈0.30`, `cos_min_recall≈0.15`, применяется в `mcp_server.main()`, пишется в db_meta.
4. Тесты: точный токен находится при низком косинусе; воздержание на шуме сохранено.

## WP4. Бриф с эпизодами

`cmd_brief`: top-5 episodic по `retention·(1+ln(1+reinforced_count))`, скоуп-фильтр проект+global, бюджет ~600 символов, вывод определённого проекта. Обновить `test_hook_cli`.
