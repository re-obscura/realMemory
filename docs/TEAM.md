# Team sharing — дизайн (этап 1 выполнен, сеть впереди)

Цель: из single-user инструмента вырастить командный слой без центральной
копии чужих данных. Личная память остаётся полностью локальной и приватной;
публикация — всегда явное действие с записью в локальный реестр.

## Принятая модель

- **Личное по умолчанию.** Обычные `memorize`/`recall` не изменились ни байтом.
- **Публикация = состояние, а не событие.** Локальная таблица `publications`
  хранит `publication_id, trace_id, project, author, published_at,
  content_hash, revoked_at`. Отзыв — tombstone (`revoked_at`), повторная
  публикация того же следа — новая строка истории. Будущая сетевая
  синхронизация строится поверх этого журнала, а не на push «в воздух».
- **Политика двухуровневая** (`~/.realmemory/team.yaml`, `team/policy.py`):
  - `shareable.projects [+ kinds + min_reinforcements]` — что *может*
    покинуть машину; TUI-переключатель правит именно это;
  - `never: {meta_tags, text_patterns}` — fail-closed и сильнее всего:
    `registry.publish` отклоняет ВЕСЬ пакет при попадании хотя бы одного
    кандидата (без частичных публикаций «через один»).
- **Атрибуция — первоклассное поле.** Колонка `author` в `memories`
  (миграция v1→v2 со страховочным бэкапом), значение — identity-файл →
  `$REALMEMORY_IDENTITY` → git config user.name. Публиковать следы с чужой
  атрибуцией запрещено.
- **Координатор (будущее)** — пассивный presence+read-cache опубликованного.
  Никогда не пишет в локальные базы и не инициирует запросы.

## Интерфейсы (сейчас)

```bash
python -m realmemory.team status --path D [--json]
python -m realmemory.team ui     --path D      # Textual: проекты/кандидаты/
                                               # превью, space/s/p/u/r/q
python -m realmemory.team policy [show|path|init]
```

MCP-сервер проставляет `author` каждой записи автоматически. Запланированные
инструменты агента — те же операции (`team_share`/`team_unshare`/`status`),
единый кодовый путь с CLI/TUI через `team/registry.py`.

## Что осознанно НЕ сделано (и почему)

- Pull-реплика кэша на клиентах (устойчивость к падению координатора)
  отложена; live-пиры частично компенсируют.
- Peer-endpoint открывает порт на машине участника — по умолчанию
  127.0.0.1; для LAN (0.0.0.0) обязателен токен и осознанный выбор.
- Чужие следы не публикуем; superseded-история не подлежит GC; рёбра L2 не
  атрибутируются по следам и угасают сами.
- Открытые вопросы перед сетью: TTL vs вечность кэша под tombstone-
  контролем; хранит ли координатор текст вместе с embedding (да, иначе поиск
  невозможен — задокументировать как «координатор хранит опубликованное»);
  контракт одинаковой версии fastembed у участников (handshake).

## Сетевой этап v0.7: координатор + sync

- **Протокол координатора** (`python -m realmemory.team.coordinator`):
  `POST /heartbeat`, `GET /presence` (TTL 90 c), `POST /publish`,
  `POST /retract`, `POST /search`, `GET /cache/dump`, `GET /health`.
  Токен опционален, но рекомендуется: заголовок `Authorization: Bearer`,
  значение из `$REALMEMORY_TEAM_TOKEN`. Состояние — sqlite-файл в `--data`.
- **Клиент** (`team/sync.py push`, CLI `sync`): отправляет И активные
  публикации, И tombstones; помечает строки `synced_at` только после успеха.
  Отзыв уже синхронизированной публикации сбрасывает маркер — tombstone
  гарантированно доезжает. Падение сети посреди синка не теряет решений:
  несинхронизированное доедет при следующем запуске.
- **recall_team**: только cached-канал с честным возрастом (`max_age_s`) и
  авторством; несовпадение эмбеддера — явная ошибка (HTTP 409), а не косинус
  от бессмысленного сравнения. Live peer-to-peer остаётся следующим шагом
  (нужен сетевой вход на машинах разработчиков).
- MCP-тул `recall_team` регистрируется только при настроенном координаторе.

## Live peer-to-peer v0.8

- **`python -m realmemory.team serve`** — демон участника: peer-endpoint
  (`POST /recall` над JOIN memories × active publications) + фоновые
  presence-хартбиты с адресом. Приватность конструктивная: личные следы
  вне публикаций не попадают в кандидаты ни на одном шаге (регресс-тест
  с личным дублем того же текста).
- **recall_team** live→cache: online-пиры с адресами опрашиваются с
  таймаутом 1.5 c (до 6 пиров), неудачи — в `peers_failed`, кэш добирает
  остальное; дедуп по (author, text); `max_age_s` = устаревание худшего
  попадания.
- **GC × команда**: доставленная публикация с локально забытым следом
  авто-отзывается следующим sync (tombstone без контента); несинхронно-
  забытая — помечается так же. Забытый автором факт команде не виден.
- **auto_sync: true** — доставка после каждого сна (хук Stop), ошибки не
  блокируют сон; путь политики: `$REALMEMORY_POLICY_PATH`.

## Ограничения честно

- UI-логика покрыта headless-смоком (Textual Pilot); раскладки/горячие клавиши
  проверяются вручную.
- ConcurrencyPublication-guard: одновременный `publish` из двух процессов
  сериализуется транзакцией стора, но повторная публикация одного следа
  создаёт две строки — история, не ошибка.
